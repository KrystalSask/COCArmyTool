# 英雄、装备与战宠识别优化执行计划

## 1. 文档用途

本文档供后续实现 agent 执行识别优化使用，内容包括：

- 当前问题定位；
- 已确认的根因；
- 各问题对应的优化实现；
- 装备识别模型的接入和部署边界；
- 任务依赖、执行顺序和验收标准。

本计划不要求重新训练战宠模型。战宠继续使用模板识别，但需要修复几何定位、候选置信度和唯一性约束。

装备模型的数据集制作和模型训练属于前序 agent 任务。本计划中的“模型接入与部署”必须等待前序 agent 交付可用模型、manifest 和预处理协议后再开始，不能提前假设模型文件或类别索引。

相关数据集标准见：

[英雄装备独立识别模型：任务需求与边界条件](./equipment-recognition-model-requirements.md)

## 2. 当前识别架构

当前主要流程如下：

```text
完整截图
  ↓
游戏画面/黑边检测
  ↓
军队面板定位
  ↓
右侧兵种、法术、攻城机器卡片检测
  ↓
左侧四列英雄装备和战宠固定框
  ↓
装备模板匹配、战宠模板匹配
  ↓
两件装备共同归属推断英雄
  ↓
人工确认和统一配兵校验
```

右侧兵种卡片目前可以使用 ONNX 分类器，入口主要在 [cardAnalysis.ts](/E:/COC/src/recognition/cardAnalysis.ts)。

英雄装备目前通过 [heroSubcardAnalysis.ts](/E:/COC/src/recognition/heroSubcardAnalysis.ts) 使用固定坐标、dHash 和 HSV 直方图匹配。英雄本身没有独立的直接图像分类器。

英雄推断目前通过两件装备的共同归属完成，相关逻辑在 [heroInference.ts](/E:/COC/src/recognition/heroInference.ts) 和 [visualEngine.ts](/E:/COC/src/recognition/visualEngine.ts)。

## 3. 已确认的问题和证据

### 3.1 样本 1：面板/英雄子框横向偏差

样本 1 现有输出：

```text
英雄 ID：7,0,1,7
英雄几何分：0.414
战宠：?, ?, ?, 9
```

面板定位候选之间的选择差距较小，说明自动定位存在不确定性。右侧兵种仍大部分识别正确，但左侧装备框明显偏向面板左侧。

该现象说明：

- 右侧卡片区域足够宽，仍能覆盖实际卡片；
- 左侧英雄装备框是固定位置，偏移后直接裁到错误内容；
- 兵种识别结果正常不能证明整个面板框正确。

### 3.2 样本 2：框位置基本可用，但装备配对错误

样本 2 现有输出：

```text
英雄 ID：7,2,7,2
装备归属重复：飞龙公爵、大守护者各出现两次
```

该样本中装备框位置相对合理，但装备模板候选之间分差很小。当前同英雄配对逻辑会把低分候选提到第一位，只因为它能和另一个槽凑成同一英雄。

典型表现：

- 某个候选原始分数约 58%，但最终选中的候选只有约 49%；
- 正确装备可能在 Top-4～Top-8 中，却被错误的同英雄组合覆盖；
- 每列独立推断后，多个列可以得到同一个英雄。

### 3.3 战宠识别失败主要是几何和模板问题

样本中战宠会出现未识别或低分，但战宠类别数量少、图标差异相对明显。

因此当前不应优先训练战宠模型。应先修复：

- 战宠框跟随英雄列校准；
- 战宠模板真实样本覆盖；
- 每个战宠的阈值和分差；
- 战宠不能重复使用的下游约束。

### 3.4 英雄候选 UI 横向溢出

现有英雄卡片四列布局在真实浏览器尺寸下出现：

- 英雄卡片内部可用宽度约 302px；
- 装备候选行实际宽度约 405px；
- 英雄网格出现额外横向滚动宽度；
- 候选行穿透相邻英雄卡片。

涉及样式主要在 [styles.css](/E:/COC/src/styles.css) 的 `.candidate-row`、`.recognized-hero-grid` 和英雄证据块规则，候选渲染在 [RecognitionReviewPanel.tsx](/E:/COC/src/components/RecognitionReviewPanel.tsx)。

## 4. 根因分析

### 4.1 面板评分偏向右侧兵种

面板候选评分中，右侧卡片结构占比明显高于英雄区域。结果是一个对兵种足够好的候选面板，可能对英雄区域已经偏移。

优化重点不是简单增加一个总分，而是让英雄列、装备行和战宠行成为独立的结构证据。

### 4.2 已搜索局部几何，但没有真正采用

当前代码会尝试多个 `dx`、`dy` 和 `spacing` 候选，但最终仍使用基准几何。候选偏移只记录到诊断信息中，没有作用于最终裁片。

需要把局部注册变成生产逻辑，并增加防止误移动的提升阈值。

### 4.3 装备模板特征不足且数据稀疏

当前装备识别主要使用：

- 64×64 归一化；
- dHash；
- HSV 直方图；
- 最近模板距离。

该方案对边框、缩放、压缩、等级数字和编辑标记敏感。现有装备观测数量有限，部分装备只有少量样本，离线模板评估不能代表新真实截图的泛化能力。

### 4.4 配对策略是局部贪心，而非全局推理

当前 [resolveEquipmentPairCandidates](/E:/COC/src/recognition/heroSubcardAnalysis.ts:25) 只在单列内部寻找合法同英雄组合。

它没有同时考虑：

- 其他三列已经使用了哪些英雄；
- 四位英雄必须互不重复；
- 当前组合是否显著优于其他组合；
- 是否应保留未知而不是强行猜测。

### 4.5 识别分数没有校准

当前 `1 - distance` 的数值被 UI 以百分比展示，但它不是经过校准的概率。不同装备、不同模板数量和不同裁片质量下，分数不可直接等价比较。

需要保留原始分数、Top-1/Top-2 分差和拒识状态。

### 4.6 唯一性校验发生得太晚

配兵校验层已经检查英雄不能重复，但识别层和一键确认逻辑没有把唯一性作为候选选择约束。

结果是错误重复英雄会先出现在识别结果和 UI 中，直到后续统一校验才暴露。

### 4.7 候选 UI 使用了不受限的最小内容宽度

候选按钮包含固定图标列和分数文本。多个候选在 flex 行中会形成较大的最小内容宽度，而父级英雄网格没有限制候选行的宽度。

这属于布局约束缺失，不是识别结果数量本身的问题。

## 5. 优化实现任务

## 5.1 任务 A：面板整体定位增强

### 实现逻辑

在面板候选评分中加入独立的英雄区域结构评分：

1. 检查四个英雄列是否存在；
2. 检查八个装备槽的宽度和间距一致性；
3. 检查四个战宠槽是否位于预期行；
4. 检查英雄区域与右侧卡片区域的相对比例；
5. 当右侧结构分数高但英雄结构分数低时，降低面板候选总分；
6. 当候选总分接近时，保留多个候选并显示面板定位不确定，而不是盲目选择。

### 解决的问题

- 样本 1 的英雄区域横向偏移；
- 兵种正确但英雄错误的“部分定位正确”现象；
- 黑边、字幕、视频画幅变化导致的面板选择不稳定。

### 注意事项

不能只提高英雄权重。英雄结构评分必须独立计算，避免错误模板匹配反过来影响面板位置。

## 5.2 任务 B：英雄区域局部几何注册

### 实现逻辑

面板选定后，对英雄区域单独寻找局部几何：

1. 生成 `dx/dy/spacing` 候选；
2. 计算八个装备框边缘对齐度；
3. 计算槽宽和槽间距一致性；
4. 计算四个战宠框与英雄列的对应关系；
5. 与基准几何比较；
6. 只有当候选在多项结构指标上稳定提升时才采用；
7. 装备框、战宠框和守护者模式框全部使用同一局部几何。

### 解决的问题

- 默认装备框稍微偏移便导致识别错误；
- 装备和战宠框之间相互错位；
- 不同 UI 缩放比例造成的固定间距误差。

### 注意事项

局部注册应优先使用边缘和网格结构，不能只依据模板匹配分数，否则可能为了匹配错误图标而移动裁片。

## 5.3 任务 C：装备模型接入前的接口冻结

此任务可以提前设计，但正式接入必须等待前序 agent 交付模型文件。

### 前置依赖

前序 agent 必须先交付：

- 可加载的 ONNX 模型；
- 类别 manifest；
- 输入尺寸和张量布局；
- RGB/BGR 约定；
- 归一化方式；
- 输出 logits/probability 说明；
- 模型版本号；
- 预处理版本号；
- 独立真实测试报告。

没有以上材料时，后续 agent 不得猜测类别索引或输入格式，也不得直接替换线上模板识别。

### 推荐适配接口

```ts
interface EquipmentPrediction {
  id: number
  score: number
  ownerHeroId: number
}

interface EquipmentRecognition {
  candidates: EquipmentPrediction[]
  source: 'onnx' | 'template'
  modelVersion: string
  preprocessingVersion: string
}
```

### 解决的问题

- 训练数据、模型输出和线上类别映射不一致；
- 模型升级后代码仍使用旧类别索引；
- 线上无法区分模型结果与模板兜底结果。

## 5.4 任务 D：装备模型影子接入

### 实现逻辑

新增装备识别运行模式：

```text
template：只运行模板识别
shadow：模型和模板同时运行，但模板仍是正式结果
onnx：模型作为正式结果，模板作为异常兜底
```

影子模式需要记录：

- 模型 Top-1 和 Top-K；
- 模板 Top-1 和 Top-K；
- 两者是否一致；
- 所属英雄是否一致；
- 分数差异；
- 输入裁片信息；
- 模型和预处理版本。

### 解决的问题

- 在不改变用户结果的情况下验证模型；
- 发现模型与训练报告不一致的真实截图；
- 判断模型是否真的优于模板，而不是只看合成测试集。

### 注意事项

影子模式应优先在两个问题样本、已有回归样本和新的独立真实样本上运行。

## 5.5 任务 E：装备模型正式接入和降级

### 正式接入逻辑

只有影子模式验证通过后，才允许启用 `onnx` 正式路径：

1. 使用统一局部几何生成装备裁片；
2. 按 manifest 规定完成预处理；
3. 执行 ONNX 推理；
4. 输出按分数降序排列的 Top-K；
5. 将类别索引映射为装备 ID；
6. 根据装备 ID 关联 `ownerHeroId`；
7. 将结果交给英雄全局推理；
8. 保存模型版本和预处理版本。

### 必须回退模板的情况

- 模型文件不存在；
- 模型加载失败；
- ONNX Runtime 初始化失败；
- 输入尺寸或通道格式不匹配；
- manifest 缺失或类别数量不一致；
- 输出索引无法映射；
- 推理异常或超时；
- 模型结果分数过低或完全无效。

回退结果必须标记为 `source: 'template'`，不能伪装成模型结果。

## 5.6 任务 F：模型资源部署

### 浏览器部署

需要验证：

- 模型位于发行构建会复制的静态资源目录；
- 构建后使用相对路径加载；
- 不依赖开发服务器路径；
- manifest 与模型文件一起发布；
- 模型请求失败时不会阻塞整页识别。

### Tauri 桌面端部署

需要在 `tauri build` 后验证：

- ONNX 文件进入最终安装包或资源目录；
- manifest 和类别映射同时存在；
- 安装后的相对路径仍然有效；
- 离线环境可以完成装备识别；
- 模型加载失败可回退模板。

### 性能和加载

视模型大小决定是否：

- 首次进入截图识别页面时懒加载；
- 使用 Web Worker 避免阻塞 UI；
- 缓存已经创建的 ONNX Session；
- 显示模型加载状态；
- 对推理设置合理超时。

## 5.7 任务 G：装备归属和四英雄全局匹配

### 推荐逻辑

不要继续使用“每个槽先取 Top-1，再判断两件装备归属”的顺序。

应改为：

1. 每个装备槽保留 Top-K 候选；
2. 对每一列、每一位英雄枚举合法的两件不同装备组合；
3. 计算该列属于该英雄的组合分数；
4. 四列一起求总分最高的组合；
5. 约束四列英雄不重复；
6. 证据不足时允许某列为未知；
7. 确定英雄后，再选择该英雄名下的具体装备。

### 评分建议

组合评分应综合：

- 两件装备的模型分数；
- Top-1/Top-2 分差；
- 两件装备是否都属于该英雄；
- 装备是否重复；
- 该英雄是否已被其他列使用；
- 是否存在明显更优的全局组合。

### 解决的问题

- 样本 2 的 `7,2,7,2`；
- 样本 1 的 `7,0,1,7`；
- 低分装备因配对关系被提升到第一名；
- 正确装备在 Top-4～Top-8 中却无法进入最终结果。

### 重要边界

四英雄唯一性是强游戏规则，但不能让唯一性掩盖“候选集中没有正确英雄”的情况。因此必须保留未知状态。

## 5.8 任务 H：置信度、分差和拒识

### 实现逻辑

装备、战宠和英雄列都应同时使用：

- Top-1 绝对分数；
- Top-1 与 Top-2 分差；
- 裁片质量；
- 框几何质量；
- 同英雄组合合法性；
- 四列全局匹配稳定性。

结果状态建议至少包括：

```text
confirmed-candidate：证据足够，可作为自动候选
ambiguous：候选接近，需要人工确认
unrecognized：没有可靠候选
geometry-warning：裁片几何质量不足
```

### 解决的问题

- 不再把低分猜测直接显示为确定英雄；
- 避免把模板距离误认为概率；
- 让用户知道错误来自分类不确定还是裁片不确定。

### 注意事项

阈值必须依据独立真实验证集设定，不得仅依据合成数据或单个样本设定。

## 5.9 任务 I：战宠模板识别优化

不训练单独战宠模型。

### 实现逻辑

- 战宠框跟随英雄局部几何；
- 统一战宠裁片预处理；
- 增加不同设备、缩放和压缩质量的真实模板；
- 为每个战宠校准阈值；
- 保留 Top-3 候选；
- 分差过小时显示待确认；
- 四位英雄不能分配同一个战宠。

### 解决的问题

- 战宠框偏移造成的未识别；
- 少量战宠模板在新设备上的匹配下降；
- 战宠重复分配。

## 5.10 任务 J：英雄候选 UI 修复

### 推荐实现

默认每个装备槽展示 Top-3，剩余候选通过“展开更多”查看。候选容器必须受英雄卡片宽度约束。

至少保证：

- `.candidate-row` 不超过父容器宽度；
- 候选按钮允许收缩或换行；
- 不覆盖相邻英雄卡片；
- 小窗口下自动变为两列或单列；
- 仍可通过下拉框选择所有装备；
- 选中候选后原图证据框定位不变。

### 解决的问题

- 当前候选行横向溢出；
- 四列英雄 UI 错位；
- 候选分数和图标被相邻卡片遮挡。

## 5.11 任务 K：识别确认和校验流程

识别页面应在进入编辑器前展示英雄唯一性和装备适用性问题。

需要：

- 重复英雄直接标记为冲突；
- 重复战宠直接标记为冲突；
- 装备跨英雄归属冲突直接标记；
- 模型/模板来源显示在诊断中；
- 一键确认不能绕过唯一性冲突；
- 未知英雄或未知装备必须保留待确认状态。

下游统一配兵校验仍然保留，识别层的检查不能替代最终领域校验。

## 6. 装备模型接入顺序和依赖关系

```text
前序 agent：生成数据集
        ↓
前序 agent：训练模型并提供 manifest/预处理协议
        ↓
冻结装备裁片和输入接口
        ↓
完成面板与英雄局部几何修复
        ↓
接入 shadow 模式
        ↓
独立真实样本对比模型和模板
        ↓
接入 ONNX 正式路径
        ↓
验证浏览器构建和 Tauri 打包
        ↓
开启模型失败回退
```

### 不得提前做的事情

- 不得猜测模型输出类别索引；
- 不得先写死一个假 manifest；
- 不得在没有真实对比结果时删除模板路径；
- 不得把模型分数直接当作百分比概率；
- 不得把模型接入和四英雄唯一匹配混写成一个不可诊断函数。

## 7. 测试与验收标准

### 7.1 几何回归

必须覆盖：

- 面板横向偏移；
- 装备框 `±8～12px` 偏移；
- 战宠框跟随偏移；
- 不同面板缩放；
- 黑边和字幕；
- saved/edit/attack 页面。

### 7.2 两个问题样本

两个样本的英雄真实顺序均应为：

```text
7,1,0,6
```

即：飞龙公爵、弓箭女皇、野蛮人之王、亡灵王子。

装备具体 ID 应以人工确认的样本标注为准，不能只用英雄 ID 正确作为完整验收。

### 7.3 模型接入

- 模型 Top-1/Top-3 与真实标签对比；
- 模型与模板分歧可追踪；
- ONNX 加载失败自动回退；
- manifest 版本不匹配时拒绝加载；
- 浏览器生产构建可加载；
- Tauri 安装包离线可加载；
- 模型推理失败不会导致整个识别页崩溃。

### 7.4 全局规则

- 四列英雄不重复；
- 四列英雄不足以确定时保留未知；
- 两件装备属于同一英雄且不重复；
- 四位英雄不能重复战宠；
- 重复和冲突在识别页面可见。

### 7.5 UI 验收

在至少以下宽度下验证：

- 1440px 以上桌面宽度；
- 1000px 左右窗口；
- 600px 以下移动宽度。

要求英雄卡片、候选行和原图定位框均不发生横向溢出或覆盖。

## 8. 推荐执行批次

### 批次一：几何与诊断

- 面板评分增加英雄结构；
- 启用英雄局部几何注册；
- 战宠框跟随局部几何；
- 增加裁片和几何诊断信息。

### 批次二：规则推理

- 装备按英雄归属计算组合；
- 四列英雄全局唯一匹配；
- 增加未知和拒识；
- 增加战宠唯一性。

### 批次三：等待模型交付后的接入

- 冻结模型 manifest 和预处理协议；
- 接入 shadow 模式；
- 真实样本对比；
- 接入 ONNX 正式路径；
- 保留模板降级。

### 批次四：部署和 UI

- 浏览器生产构建验证；
- Tauri 安装包资源验证；
- 模型懒加载/Worker 优化；
- 修复候选 UI 溢出；
- 完成完整 E2E 回归。

## 9. 不在本轮范围内的事项

- 战宠专用模型训练；
- 直接训练英雄皮肤分类模型；
- 重写右侧兵种 ONNX 分类器；
- 在没有模型 artifact 的情况下提前接入装备 ONNX；
- 用唯一性规则强行替代底层识别质量；
- 删除现有模板识别兜底。

## 10. 完成定义

本计划完成的最低标准是：

1. 两个问题样本不再出现重复英雄；
2. 装备框轻微偏移不会立即导致整列英雄错误；
3. 不确定结果能明确显示为待确认；
4. 四列英雄全局唯一规则参与候选选择；
5. 战宠仍使用模板，但框定位和唯一性正确；
6. 装备模型可以通过 manifest 正确加载，且失败时回退模板；
7. 浏览器和 Tauri 构建都能找到模型资源；
8. 英雄候选 UI 不再横向溢出；
9. 所有模型、模板、几何和规则来源都能在诊断信息中区分。
