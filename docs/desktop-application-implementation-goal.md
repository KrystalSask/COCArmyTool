# COC 配兵助手：桌面版整合与识别兼容性实现目标

## 1. 文档目的

本文档定义 COC 配兵助手下一阶段的产品目标、技术边界、实施顺序和验收标准。后续开发应以本文档作为范围基线，避免同时推进移动端、云端和桌面端而造成目标扩散。

本阶段只聚焦三条主线：

1. 整合功能入口和编辑流程，降低页面间的重复与割裂。
2. 将现有 React/Vite 项目封装为可直接安装和运行的 Windows 桌面应用。
3. 提高截图识别对不同分辨率、宽高比和 PNG/JPEG/WebP 格式的兼容性。

实施顺序固定为：

```text
功能界面整合
    ↓
Windows 桌面封装与安装包
    ↓
识别图像标准化
    ↓
多分辨率与 JPEG/WebP 回归优化
```

除非出现阻塞性技术问题，不应越过前一阶段直接大规模开发后一阶段。

## 2. 已确认决策

### 2.1 Windows 支持范围

- 支持 Windows 10、Windows 11。
- 首期只构建 x64 版本。
- 不支持 Windows 7、Windows 8、Windows on ARM。
- 普通用户不需要安装 Node.js、npm、Python 或启动本地开发服务器。

### 2.2 桌面应用交付形式

- 使用 Tauri 2 封装现有 React/Vite 应用。
- 正式交付物为 Windows `Setup.exe` 安装程序。
- 安装后提供开始菜单入口、桌面快捷方式和标准卸载入口。
- 首期不要求免安装便携版。
- 首期不制作 MSI。
- 首期不实现应用内自动更新。
- 首期不购买或接入 Windows 代码签名证书；测试分发时允许出现 SmartScreen 未知发布者提示。

### 2.3 功能信息架构

应用主结构收敛为：

1. 新建方案。
2. 配兵编辑器。
3. 方案库。

“新建方案”提供链接导入、截图识别和手动创建三个入口。三种来源最终进入同一个配兵编辑器。截图识别仍保留独立的候选核对阶段，核对完成后再进入编辑器。

### 2.4 图片识别支持范围

- 支持 PNG、JPG/JPEG、WebP。
- 输入必须是完整、未裁剪的横屏游戏截图。
- 兼容不同像素分辨率和常见横屏宽高比。
- JPEG 首期重点保证质量 85 及以上的图像。
- 严重压缩、经过多次转发、模糊或裁剪的图片可以尝试识别，但不承诺自动识别成功。
- 所有真实识别结果继续保留人工确认。
- 容量与英雄规则校验、链接生成后回环校验继续作为强制安全门槛。

## 3. 本阶段不做的内容

以下事项明确推迟，不进入本轮开发：

- 手机端专用界面和交互重构。
- Android APK、AAB 或 iOS 应用打包。
- Capacitor、原生 Android、原生 iOS 开发。
- 用户账号、云同步、云备份和服务器端截图识别。
- 社区发布、评论、点赞或在线方案市场。
- Windows ARM、macOS、Linux 版本。
- Microsoft Store 上架。
- 自动更新服务。
- Windows 代码签名。
- 对残缺截图、竖屏截图和游戏画面照片的正式支持。
- 取消识别结果的人工确认门槛。

若后续需要其中任何一项，应单独形成目标文档和验收标准，不在本阶段顺带实现。

## 4. 当前状态与主要问题

### 4.1 现有能力

- React 19、TypeScript、Vite 构建体系已经可用。
- 已支持国服 `CopyArmy` 链接解析和生成。
- 已有完整配兵计算器、容量校验和英雄配置校验。
- Dexie/IndexedDB 已用于保存本地方案。
- 已有热门方案与本地方案库。
- 已有截图预检、面板定位、卡片切分、图标候选、数量识别和人工核对流程。
- 文件选择器已经接受 PNG、JPEG 和 WebP。
- 已有 Vitest 和 Playwright 测试基础。

### 4.2 当前问题

#### 功能界面

- “导入链接”“截图识别”“配兵计算器”按技术来源分成独立页面，但业务目标相同。
- 多个页面分别承担预览、校验、复制和继续编辑操作，用户需要理解页面边界。
- 状态提示、主要操作和返回路径缺少统一约定。
- `styles.css` 中存在多轮视觉样式和媒体查询叠加，维护成本较高。

#### Windows 使用

- 普通用户需要安装 Node.js、安装依赖、执行 npm 命令并通过浏览器访问。
- 应用没有标准安装、快捷方式、卸载和版本信息。
- 浏览器 PWA 缓存机制与未来桌面包资源加载机制需要分离。
- 浏览器 IndexedDB 与 Tauri WebView 数据目录相互独立，需要数据迁移入口。

#### 截图识别

- 当前布局识别仍依赖已采样设备画像和固定布局定义。
- 不同分辨率、缩放、宽高比和留黑可能影响区域定位。
- JPEG 有损压缩会影响卡片边缘、颜色、图标模板和数量字形。
- 缺少统一的格式/方向/尺寸标准化层。
- 缺少面向多分辨率和压缩质量的系统化回归矩阵。

## 5. 总体产品流程

### 5.1 主导航

桌面版主导航只保留三个一级入口：

| 一级入口 | 职责 | 不承担的职责 |
| --- | --- | --- |
| 新建方案 | 选择链接、截图或手动创建方式 | 不长期保存独立编辑状态 |
| 配兵编辑器 | 修改、校验、保存和复制当前方案 | 不展示完整历史方案列表 |
| 方案库 | 浏览、筛选、复制、删除和继续编辑 | 不维护第二套编辑器 |

### 5.2 链接导入流程

```text
新建方案
  → 粘贴 CopyArmy 链接
  → 解析并显示摘要/错误
  → 进入配兵编辑器
  → 校验、修改、填写方案信息
  → 保存或复制链接
```

链接解析失败时停留在新建方案页，展示明确错误，不创建空编辑状态。

### 5.3 截图识别流程

```text
新建方案
  → 选择完整横屏截图
  → 图像预检和标准化
  → 面板定位、卡片切分和候选识别
  → 人工核对所有候选
  → 生成 ArmyComposition
  → 进入配兵编辑器
  → 校验、补充信息、保存或复制链接
```

截图核对页面只负责识别证据和候选确认。方案名称、标签、备注、最终保存和最终复制统一放在配兵编辑器处理。

### 5.4 手动创建流程

```text
新建方案
  → 选择“手动创建”
  → 使用空白 ArmyComposition 打开编辑器
  → 完成配兵配置
  → 保存草稿或复制有效链接
```

### 5.5 方案库流程

- 内置热门方案和“我的方案”仍可分区展示。
- 点击“继续编辑”必须将方案复制到统一编辑器状态。
- 完整方案可直接复制链接。
- 草稿必须进入编辑器补全后才能复制链接。
- 删除本地方案必须二次确认。
- 方案库不引入另一套字段编辑与配兵编辑逻辑。

## 6. 阶段一：功能界面整合

### 6.1 实现目标

- 用户不需要理解“导入页、识别页、计算器页”之间的技术差异。
- 三种创建方式最终汇入同一个编辑器。
- 页面上始终能辨认当前步骤、配兵是否有效以及下一步可以做什么。
- 优先改善 Windows 桌面窗口体验，不开展手机端专项重构。

### 6.2 建议代码结构

```text
src/
  App.tsx
  pages/
    CreatePage.tsx
    ScreenshotRecognitionPage.tsx
    EditorPage.tsx
    LibraryPage.tsx
  components/
    AppHeader.tsx
    CreationMethodCard.tsx
    EditorActionBar.tsx
    StatusMessage.tsx
    CompositionPanel.tsx
  state/
    editorSession.ts
```

文件名可根据实施情况调整，但职责边界必须保持一致。

### 6.3 编辑会话模型

需要引入统一的编辑会话概念，至少包含：

```ts
interface EditorSession {
  source: 'link' | 'screenshot' | 'manual' | 'library'
  recordId?: string
  composition: ArmyComposition
  originalLink?: string
  dirty: boolean
}
```

要求：

- 链接、截图、手动和方案库入口通过同一接口创建编辑会话。
- 页面跳转不能通过互不关联的临时 state 拼装编辑器参数。
- 修改配兵或方案字段后将会话标记为 `dirty`。
- 离开未保存编辑会话时提示用户确认。
- 保存成功后更新 `recordId` 并清除 `dirty`。
- 新建其他方案前必须处理当前未保存会话。

首期编辑会话可以只存在 React 内存中，不要求崩溃恢复；但代码边界应允许未来加入会话持久化。

### 6.4 统一操作层级

编辑器操作按以下优先级排列：

1. 主操作：保存方案或复制有效链接。
2. 次操作：返回来源、重置、另存副本。
3. 危险操作：放弃修改、删除方案。

要求：

- 同一页面最多只有一个视觉上最强的主按钮组。
- “无法复制”必须显示具体原因，不只禁用按钮。
- 保存草稿不要求配置完整。
- 复制链接必须通过现有全部校验。
- 操作成功、警告、处理中和失败状态使用统一组件与颜色语义。

### 6.5 样式整理

- 保留现有木质游戏风格，不进行全新品牌设计。
- 将基础变量、布局、组件、页面和响应式规则按章节整理。
- 移除被后续规则完全覆盖的旧样式。
- 避免同一选择器在多个远距离区块反复覆盖。
- 保证 100%、125%、150% Windows 显示缩放下可用。
- 重点验证 1280×720、1920×1080、2560×1440 窗口。
- 最小窗口尺寸由实际布局测试确定，首期建议不低于 1100×700。

### 6.6 阶段一验收标准

- 主导航只显示“新建方案、配兵编辑器、方案库”。
- 三种来源都可以进入同一个编辑器组件。
- 截图候选确认后不在识别页重复维护方案保存表单。
- 从方案库继续编辑时不会修改原记录，直到用户明确保存。
- 未保存修改离开时有确认提示。
- 所有现有链接解析、校验、保存和复制功能继续工作。
- 单元测试和端到端测试通过。
- 三档目标分辨率和三档 Windows 显示缩放完成手工验收。

## 7. 阶段二：Windows 桌面封装

### 7.1 技术方案

采用 Tauri 2：

- React/Vite 继续作为前端界面和业务逻辑载体。
- Tauri 使用 Windows WebView2 呈现界面。
- Rust/Tauri 层首期只承担窗口、打包和必要的系统集成。
- 不将配兵解析、校验或视觉识别算法迁移到 Rust。

### 7.2 目录和脚本目标

```text
src-tauri/
  Cargo.toml
  tauri.conf.json
  capabilities/
  icons/
  src/

package.json scripts:
  desktop:dev
  desktop:build
```

期望命令：

```powershell
npm run desktop:dev
npm run desktop:build
```

`desktop:build` 应先完成 TypeScript/Vite 生产构建，再生成 Windows x64 NSIS 安装程序。

### 7.3 应用标识与版本

- 产品名称：`COC 配兵助手`。
- 应用短名称：`配兵助手`。
- Bundle Identifier 应使用稳定的反向域名形式，确定后不得随意更改。
- `package.json` 与 Tauri 配置使用同一应用版本。
- 应用设置或关于区域显示版本号。
- 游戏数据版本与应用版本分开显示，避免混淆。

### 7.4 窗口行为

- 首次启动使用适合桌面的默认窗口尺寸。
- 设置合理最小尺寸，防止关键操作被压缩到不可用。
- 记忆窗口大小和位置属于可选优化，不作为首期阻塞项。
- 外部作者链接和粉丝政策链接必须通过系统默认浏览器打开。
- 关闭窗口前若存在未保存编辑会话，需要提示确认。

### 7.5 Service Worker 分流

浏览器/PWA 与 Tauri 必须采用不同策略：

- 浏览器模式继续注册 PWA Service Worker。
- Tauri 模式不注册 Service Worker。
- 桌面应用资源由安装包和 Tauri 协议直接提供。
- 应用升级后不得因为旧 Service Worker 缓存继续加载旧前端资源。

平台检测应封装为独立工具，不应在业务组件中散布环境判断。

### 7.6 本地数据与迁移

Tauri WebView 中的 IndexedDB 可以继续使用，但数据位置与普通浏览器不同。

桌面打包前必须增加最小数据迁移能力：

- 导出全部本地方案为一个 JSON 文件。
- 导入符合格式的 JSON 文件。
- 备份中包含格式标识、格式版本、导出时间和方案列表。
- 导入时校验字段结构和配兵结构。
- 无效文件不得写入数据库。
- 同 ID 冲突默认保留更新时间较新的记录；无法判断时保留导入副本并生成新 ID。
- 导入失败不得破坏现有数据。

建议格式：

```json
{
  "format": "coc-army-assistant-backup",
  "version": 1,
  "exportedAt": "2026-08-12T00:00:00.000Z",
  "records": []
}
```

首期继续使用 IndexedDB，不为了桌面封装改成 SQLite。未来只有在数据规模、查询或原生备份需求明确时才评估数据库迁移。

### 7.7 文件和剪贴板能力

- 截图文件选择在桌面包内必须正常工作。
- PNG、JPEG、WebP 解码行为应与浏览器开发环境一致。
- 复制配兵链接应写入 Windows 剪贴板。
- JSON 导入导出优先使用 Tauri 文件对话框和文件系统能力；浏览器模式保留 Web API 回退。
- 系统能力通过 `platform` 或 `adapters` 层封装，不让页面直接绑定某一种运行环境。

### 7.8 安装程序目标

正式产物示例：

```text
COC配兵助手_0.2.0_x64-setup.exe
```

安装程序应：

- 安装到标准用户应用目录。
- 创建开始菜单入口。
- 创建桌面快捷方式。
- 注册标准卸载项。
- 在 WebView2 缺失时执行 Tauri 推荐的安装策略。
- 升级安装同一应用标识时保留 WebView 数据目录。

### 7.9 阶段二验收标准

- 干净的 Windows 10/11 x64 环境无需 Node.js 即可安装和运行。
- 安装、启动、关闭、再次启动和卸载流程正常。
- 开始菜单和桌面快捷方式可用。
- 所有核心功能在断网环境下可用。
- 保存的方案在重新启动后仍存在。
- 覆盖升级安装后方案仍存在。
- 浏览器导出的 JSON 可以导入桌面应用。
- 截图选择、识别、保存和复制链接正常。
- 外部链接使用默认浏览器打开。
- Tauri 模式不会注册 PWA Service Worker。
- 生成的正式交付物只有 Windows x64 `Setup.exe`；其他安装形式不作为验收要求。

## 8. 阶段三：识别输入标准化

### 8.1 核心原则

后续识别算法不应直接适配每一个设备的原始像素坐标，而应先将输入图像转换为统一的标准识别空间：

```text
源文件解码
  → 方向与颜色标准化
  → 输入尺寸和完整性检查
  → 游戏面板定位
  → 面板裁切和比例归一化
  → 标准识别画布
  → 区域切分、图标匹配和数量识别
```

设备画像和已有固定布局继续保留，但定位角色由“主要依据”逐步调整为“快速路径和失败回退”。

### 8.2 支持格式

| 格式 | 首期状态 | 说明 |
| --- | --- | --- |
| PNG | 正式支持 | 无损基准格式 |
| JPG/JPEG | 正式支持 | 重点保证质量 85 及以上 |
| WebP | 正式支持 | 包含常见有损和无损 WebP |
| HEIC/HEIF | 不支持 | 首期不引入额外解码器 |
| BMP/TIFF/GIF | 不支持 | 不属于游戏截图主要来源 |

文件扩展名不能作为唯一依据，应同时检查 MIME 类型和实际解码结果。无法解码的文件必须给出可理解错误。

### 8.3 解码与方向处理

- 使用浏览器/WebView 图像解码能力得到统一像素缓冲。
- 处理 JPEG EXIF 方向，确保进入识别管线时方向已经正确。
- 统一到 sRGB 语义下的 RGBA 像素数据。
- 不因是否含透明通道改变后续算法行为。
- 对超大图片设置像素总量上限，避免内存峰值失控。
- 预览图可以缩小，但识别输入不得因为预览优化被重复有损压缩。

### 8.4 面板定位

面板定位应由多类证据共同决定：

- 页面整体横屏比例。
- 木质面板的主要颜色和边缘结构。
- 页面类型控件或已知锚点。
- 卡片行的周期性结构。
- 容量栏、英雄区等局部锚点。

输出至少包含：

```ts
interface LocatedPanel {
  bounds: Rect
  pageType: 'saved' | 'edit' | 'unknown'
  confidence: number
  evidence: PanelEvidence[]
}
```

要求：

- 不能只通过原始分辨率映射到设备名称。
- 不能只使用单个精确 RGB 颜色判断。
- 定位失败时不得继续给出高置信度配兵结果。
- 低置信度定位必须要求用户重新选择图片或进入调试/人工确认路径。

### 8.5 标准识别空间

- 面板定位完成后，将有效面板缩放到固定逻辑尺寸。
- 区域定义使用 0～1 相对坐标或标准逻辑像素。
- 缩放算法需分别评估图标识别和小数字识别；两者可以使用不同的派生图像。
- 所有卡片区域、数量角标、英雄子卡片都从标准空间派生。
- 不允许在新的识别模块中继续添加未经归一化的设备绝对坐标。

### 8.6 保留回退路径

- 已验证的 iPhone/iPad 固定布局可作为快速候选。
- 快速候选仍需经过面板证据校验。
- 通用定位失败但设备画像匹配时，可以采用固定布局并降低置信度。
- 无论走通用路径还是固定路径，最终都使用同一标准识别空间和人工确认模型。

### 8.7 阶段三验收标准

- PNG、JPEG、WebP 输入均通过同一标准化接口。
- 同一截图的不同尺寸版本可以定位到等价面板区域。
- 图像方向错误不会进入后续卡片识别。
- 区域切分不依赖具体设备像素宽高。
- 已有 13 张样本的结果不发生不可接受回退。
- 现有容量、英雄规则和链接回环安全门槛保持不变。
- 定位和标准化模块具有独立单元测试。

## 9. 阶段四：多分辨率和有损压缩识别优化

### 9.1 样本矩阵

至少覆盖以下原始尺寸或等价比例：

- 1280×720。
- 1920×1080。
- 2560×1440。
- 已有 iPhone 横屏截图。
- 已有 iPad 横屏截图。
- 后续收集到的其他完整横屏截图。

测试重点是宽高比和 UI 布局，不以设备型号数量作为唯一覆盖指标。

### 9.2 自动派生样本

从每张有标准答案的原始样本生成：

- 原始 PNG 或等价无损版本。
- JPEG 质量 95。
- JPEG 质量 85。
- JPEG 质量 70，用作非承诺范围压力测试。
- WebP 高质量有损版本。
- 75%、50% 缩放版本。
- 轻微亮度变化版本。
- 轻微对比度变化版本。
- 轻微模糊版本。

派生脚本必须记录来源样本、变换参数和输出文件摘要，避免将派生图误认为新的独立真实样本。

### 9.3 抗压缩处理

图标和数量识别可以采用不同预处理：

#### 图标匹配

- 统一候选图标尺寸。
- 评估亮度或颜色归一化。
- 允许轻度模糊降低 JPEG 块边界干扰。
- 避免精确像素相等判断。
- 比较 Top-1、Top-2 分差，而不仅是绝对分数。
- 分差不足时强制人工确认。

#### 数量识别

- 在标准化角标区域内进行局部对比度增强。
- 使用自适应或多阈值二值化，不绑定单一白色 RGB。
- 清理小面积 JPEG 噪点。
- 保留字形连通域和候选分数用于调试。
- 数量结果必须继续接受容量规则的交叉检查。

### 9.4 识别指标

评估报告至少输出：

- 输入格式与压缩质量。
- 面板定位成功率。
- 页面类型识别准确率。
- 卡片检测召回率和误检数。
- 图标 Top-1 准确率。
- 图标 Top-3 覆盖率。
- 数量识别准确率。
- 英雄装备、战宠和模式识别准确率。
- 完整配兵零人工修改通过率。
- 进入人工确认但最终可正确导出的比例。
- 平均处理时间和峰值内存的可观察近似值。

### 9.5 首期质量门槛

以下门槛作为阶段目标；若真实样本不足，应标记为“样本不足”，不得用派生样本替代真实泛化结论：

- 支持范围内图片的面板定位成功率不低于 98%。
- 卡片检测召回率不低于 98%。
- 图标 Top-3 覆盖率不低于 98%。
- 数量识别准确率不低于 95%。
- JPEG 质量 85 的核心指标相对无损基准下降不超过 3 个百分点。
- 任何低置信度结果不得绕过人工确认。
- 任何校验无效或链接回环不一致的结果不得复制链接。

这些指标不表示必须全部自动通过。首期优先保证“不会静默导出错误结果”，其次再提高自动命中率。

### 9.6 阶段四验收标准

- 自动评估脚本可重复生成派生样本和报告。
- 报告按格式、分辨率、页面类型和压缩质量分组。
- JPEG 质量 85 及以上达到首期质量门槛。
- PNG 和 WebP 不低于各自基准门槛。
- JPEG 质量 70、二次压缩等压力样本失败时显示低置信度或要求重新上传，不产生错误的高置信度导出。
- 识别失败信息能够区分格式、完整性、面板定位和候选置信度问题。

## 10. 跨阶段代码边界

建议最终保持以下分层：

```text
UI 页面和组件
    ↓
编辑会话与应用流程
    ↓
配兵领域模型、解析和校验
    ↓
存储 / 剪贴板 / 文件等平台适配器

截图页面
    ↓
图像解码与标准化
    ↓
面板定位与区域切分
    ↓
图标、数量和英雄识别
    ↓
统一候选与人工确认模型
    ↓
ArmyComposition 与领域校验
```

约束：

- React 页面不得直接实现配兵协议解析规则。
- Tauri 命令不得包含重复的配兵校验逻辑。
- 识别模块不得直接写入数据库。
- 存储模块不得依赖 React 组件。
- 图像标准化与视觉识别必须可在测试中独立调用。
- 浏览器和 Tauri 的差异通过平台适配器处理。

## 11. 测试策略

### 11.1 单元测试

- 编辑会话来源、脏状态和保存状态。
- 链接、截图和方案库进入统一编辑器。
- JSON 备份格式校验和冲突合并。
- 平台检测和 Service Worker 注册条件。
- 图片 MIME、解码、方向和尺寸限制。
- 面板相对坐标与标准空间映射。
- JPEG/WebP 派生样本结果。

### 11.2 组件测试

- 新建方案三入口。
- 编辑器校验原因和操作状态。
- 未保存离开提示。
- 截图候选确认后进入编辑器。
- 数据导入错误不会覆盖现有数据。

### 11.3 端到端测试

至少覆盖：

1. 链接导入、编辑、保存、重开方案和复制链接。
2. 手动创建草稿、保存、补全和复制链接。
3. 截图预检、候选确认、进入编辑器和导出。
4. 导出 JSON、清空测试数据库、重新导入并核对记录。
5. Tauri 桌面环境的文件选择和剪贴板。

### 11.4 Windows 安装测试

建议使用干净虚拟机或独立测试账户验证：

- Windows 10 x64。
- Windows 11 x64。
- WebView2 已存在。
- WebView2 缺失或版本过旧的安装路径。
- 覆盖安装旧版本。
- 断网启动。
- 中文用户名和包含空格的用户目录。
- 100%、125%、150% 显示缩放。

## 13. 风险与控制措施

| 风险 | 影响 | 控制措施 |
| --- | --- | --- |
| 界面整合同时重写业务逻辑 | 回归范围过大 | 保留领域层，只重组入口和状态流 |
| Tauri WebView 数据与浏览器隔离 | 用户历史数据看不到 | 桌面封装前完成 JSON 导入导出 |
| 未签名安装包触发 SmartScreen | 用户不敢安装 | 小范围分发时提供校验值和说明；公开发布前再签名 |
| Service Worker 缓存旧资源 | 升级后加载旧页面 | Tauri 环境禁止注册 Service Worker |
| JPEG 压缩导致错误高置信度 | 生成错误配兵链接 | 分差门槛、人工确认、领域校验和链接回环 |
| 派生样本造成指标虚高 | 对真实设备泛化不足 | 派生数据只测鲁棒性，真实设备样本单独统计 |
| 设备画像无限增长 | 维护成本持续上升 | 通用面板定位和标准空间作为主路径 |
| 大图造成内存峰值 | 桌面应用卡顿或崩溃 | 输入像素上限、分阶段画布释放和性能记录 |

## 15. 最终完成标准

本阶段只有同时满足以下条件才视为完成：

1. 普通用户可以通过 Windows `Setup.exe` 安装并从桌面直接打开应用。
2. 用户不需要安装开发工具或运行命令。
3. 链接、截图、手动和方案库四种来源统一进入同一个配兵编辑器。
4. 本地方案在重启和覆盖升级后不会丢失，并可通过 JSON 迁移。
5. 完整 PNG、质量 85 及以上 JPEG 和 WebP 可以进入同一识别管线。
6. 识别不再以单一设备绝对像素坐标作为唯一依据。
7. 支持范围内的多分辨率样本达到既定质量门槛。
8. 低置信度、校验失败或链接回环失败的结果无法直接导出。
9. 单元、组件、端到端、安装和识别回归测试均有可重复执行的结果。
10. 移动端、云端和自动更新没有被混入本阶段实现范围。
