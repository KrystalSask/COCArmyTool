# 截图识别回归修复：任务边界与实施计划

## 1. 文档定位

本文档供后续实现 agent 直接执行，目标是修复当前完整截图识别链路的回归，恢复并提升以下能力：

- 完整木质军队面板外框定位；
- `attack`、`saved`、`edit` 布局判断；
- 兵种、法术、攻城机器和援军卡片分割；
- 卡片类别与数量识别；
- 装备 ONNX 识别、英雄归属推断和保守拒识；
- 动态容量上限读取、保守纠错和人工审核；
- 真实回归集和 Release 门禁。

本文档建立在 2026-08-28 的真实运行审计及用户确认之上。若与
[英雄、装备与战宠识别优化执行计划](./hero-equipment-recognition-optimization-plan.md)
存在冲突，以本文档为准，尤其是装备模型与模板分歧时的处理方式。

本计划仅定义任务边界和实施顺序，不代表当前代码已修复，也不授权发布远程 Release。

## 2. 已确认的产品决策

以下决策已经确认，实施 agent 不应再次自行改变：

1. 允许选择性回退造成识别退化的现有改动，但必须通过隔离 A/B 证明，不得破坏无关功能。
2. `recognition-samples/test_data` 中除样本 7 外的 11 张干净截图将人工标注为强回归集。
3. 样本 7 含烧录的调试框和序号，仅作为污染/压力样本，不要求与干净截图同等准确。
4. 面板目标框是游戏中的完整木质军队面板外边界，必须覆盖四位英雄、全部军队区域和底部操作区域。
5. 装备 ONNX 是正式视觉来源；模板只做影子对照，不得因类别或英雄归属分歧覆盖有效 ONNX 结果。
6. 若装备模型不可加载，模板可以提供“降级审核候选”，但不得自动确认装备或据此自动确认英雄。
7. 一件装备证据足够强时，可以先确定英雄归属，再在同英雄装备中选择另一槽相对可靠的候选；第二槽证据仍不足时必须保留待确认。
8. 不新增英雄头像分类器。英雄皮肤变化大，英雄继续由装备归属推断。
9. 容量校验目标是画面中斜杠后的容器上限，例如 `300/352` 的目标是 `352`。
10. 容量不是固定常量。应优先读取每张截图显示的分母；读取失败时不得用项目默认值强行纠正识别结果。
11. 容量纠错以已识别类别为主要锚点，优先修正低置信度或明显错误的数量；类别修正必须更保守。
12. 后续仍有人工审核，因此不确定结果应拒识或标记待确认，不能为了凑满容量强行生成“合法但错误”的结果。
13. 不要求所有 42 类装备都具备同等真实样本覆盖，但强回归集内出现的装备必须满足验收要求。

### 3.2 布局判断错误

样本 2、10、11 画面中均有进攻按钮，但当前预检判定为 `saved`。其中样本 10 自动重选面板后，左边界从约 `0.2090` 移动到 `0.2669`，产生整图约 5.8% 的横向偏差。

当前流程先依据粗面板判断布局，再使用该布局对多个面板候选评分。面板候选变化后不会重新判断布局，形成错误的单向依赖：

```text
粗面板错误
  → 布局错误
  → 使用错误布局投影卡片和英雄结构
  → 错误候选获得较高结构分
  → 最终面板进一步偏离
```

### 3.3 面板候选没有拒识门槛

样本 7、9、11、12 的前两名面板分差约为 `0.0014`、`0.0082`、`0.0058`、`0.0145`。当前逻辑仍直接选择第一名并继续识别，没有把低分差视为面板不确定。

### 3.4 装备模板回退会放大错误

当前 `来源：模板 · 与模板分歧` 的实际含义是：ONNX 与模板 Top-1 不一致，系统随后选择了模板。若模板错误产生两件同属蛮王的装备，英雄会进一步被推断为蛮王，即使 ONNX 原本给出了咏王方向的候选。

该行为必须取消。模板分歧只能作为诊断证据，不能覆盖有效 ONNX 结果。

### 3.5 现有测试不能证明端到端正确

- `test_data` 只有样本 1 存在较完整的类别和数量断言；
- 样本 1～4 的其他断言主要检查卡片槽位数量；
- 样本 11～12 只检查英雄子框数量；
- 样本 5～6 的部分测试允许已知错误结果，只要求产生容量警告；
- 样本 7 只检查面板没有选到黑色视频边界；
- 第二批浏览器评估仅写报告，没有准确率门槛；
- 455 张模型一致性测试使用预裁卡片，不覆盖完整截图、布局和面板链路；
- 已参与模板/reference 构建的数据不能当作独立盲测集。

因此，测试数量通过不得继续作为 Release 结论，必须改为基于真实标签和结果质量的门禁。

## 5. 实施原则

### 5.1 先建立真值，再改算法

不得先改代码再根据输出补标签。人工标签必须直接来自原始截图、游戏图鉴和可见数量。

### 5.2 面板、布局、分割、分类分层诊断

每层必须能单独输出结果：

```text
游戏有效画面
  → 面板外框候选
  → 每个候选的布局候选
  → 卡片/英雄几何
  → 类别
  → 数量
  → 容量纠错
  → 装备归属和英雄推断
```

不得使用最终类别正确率反向掩盖面板错误，也不得使用容量合法性掩盖视觉分类错误。

### 5.3 保守纠错优先于强制合法化

容量规则只能在视觉候选已经提供足够证据时选优。没有可靠候选时应输出未知，而不是创造一个满足容量的组合。

### 5.4 所有自动变化必须可追踪

每个被自动调整的数量或类别必须保留：

- 原始 Top-1；
- 原始候选与分数；
- 调整后的值；
- 使用的容量上限；
- 调整原因；
- 是否存在唯一合法解；
- 调整置信度。

## 6. 分阶段实施计划

## 阶段 0：工作区保护与双基线

### 任务

1. 记录当前 `git status`、相关文件 diff、模型文件哈希和现有测试结果。
2. 不得对当前脏工作区执行 `reset --hard`、`checkout --` 或清理用户文件。
3. 在隔离 worktree/副本中构造两个可运行基线：
   - 当前实现；
   - 兵种、法术和攻城仍稳定的最后可识别版本或选择性旧实现。
4. 对同一人工真值集输出逐层差异，不只比较最终测试是否通过。

### 交付物

- `baseline-current.json`
- `baseline-stable.json`
- 逐样本差异报告；
- 建议回退的具体函数/分支及证据。

### 门禁

在没有 A/B 结果前，不允许大范围重写识别管线。

## 阶段 1：建立权威回归标签

### 1.1 强回归集

为 `test_data` 的 11 张干净截图建立独立标签，至少包含：

- 文件名和图像哈希；
- 是否干净截图；
- 游戏有效画面框；
- 完整木质面板外框，像素与归一化坐标各一份；
- 正确布局；
- 每个容量标题的分子与分母；
- 四个区域按画面顺序排列的卡片类别 ID、数量和卡片框；
- 四列英雄顺序；
- 每列两件装备 ID；
- 战宠 ID；
- 咏王模式（若可见）；
- 无法确定项及人工说明。

标签必须通过容量计算器验证，但容量只能用于发现标注错误，不能反向猜测不可见类别。

### 1.2 样本 7 压力标签

样本 7 单独标记为 `contaminated-overlay`，记录：

- 烧录的黄色面板框；
- 青色卡片框及序号；
- 字幕和黑边；
- OCR 不得将序号与真实数量拼接；
- 若无法可靠分离，数量应为待确认。

### 交付物

- 机器可读标签文件；
- 每张图的人工框叠加预览；
- 标注说明和容量校验报告。

### 门禁

11 张强回归标签未完成前，不得声称任何面板、卡片或装备修复已经验收。

## 阶段 2：布局与完整面板联合定位

### 2.1 候选联合评估

每个面板候选都必须分别评估 `attack`、`saved`、`edit`，不能先冻结一个布局再评估全部面板。

联合候选至少包含：

- 面板外边界连续性；
- 木质区域与边框证据；
- 顶部标签/关闭按钮锚点；
- 四列英雄区域比例；
- 主军、法术、攻城、援军四行相对位置；
- 底部操作区；
- 不依赖语言的按钮形状、位置和结构；
- 绿色按钮与浅色按钮两种视觉样式；
- 黑边、字幕和视频 UI 排除证据。

### 2.2 严格面板目标

面板框必须对齐人工标注的完整木质外框。不得把以下位置作为面板左边界：

- 第一张英雄卡片左边缘；
- 右侧主军区域左边缘；
- 内部垂直分隔线；
- 视频黑边或字幕边缘。

### 2.3 不确定性处理

- 前两名候选差距不足时，不得静默当作高置信度；
- 可以继续生成审核候选，但必须标记 `panel-ambiguous`；
- 若候选框差异会改变布局或容量结果，不允许“一键确认全部”；
- 用户手动锁定面板后，不得再次注册或替换该框；
- 手动框应用后需要重新判断布局。

### 2.4 验收指标

对 11 张干净截图：

- 布局 11/11 正确；
- 面板 IoU 不低于 0.96；
- 任一边相对整图误差不高于 1%；
- 手动锁框后坐标保持不变；
- 面板变化后布局会重新计算。

若个别截图因真实边框不可见无法达到几何指标，必须在标签中说明，并以可见边界误差替代，不能放宽全部样本门槛。

## 阶段 3：恢复卡片分割与裁片稳定性

### 3.1 选择性回退

重点 A/B 以下行为：

- 单数量徽标条件下基于白色组件截断尾部；
- 援军弱尾部裁剪；
- 攻城尾部按已识别数量裁剪；
- 面板重选后统一拉伸到标准空间；
- 卡片边缘序列和数量徽标序列的优先级。

只有同时改善强回归集且不破坏已有独立样本的规则才能保留。为单张样本增加的条件必须有跨样本结构依据。

### 3.2 分割原则

- 卡片是否存在主要由边框、间距和连续结构决定；
- OCR 数量不能凭空增加卡片；
- 容量不能凭空增加或删除卡片；
- 尾部删除必须有明确的“非卡片”证据；
- 污染样本中的调试框序号不能被当作数量徽标；
- 检测器应输出每个槽的存在分、边框分、数量徽标分和推断状态。

### 3.3 裁片质量门禁

在调用类别模型或 OCR 前，对裁片检查：

- 是否覆盖合理的卡面范围；
- 是否含预期边框/背景；
- 是否被截断；
- 是否主要为字幕、黑边或调试标记；
- 尺寸和缩放是否在训练分布附近。

裁片质量不足时应标记几何问题，不应让封闭分类器强行返回一个高置信类别。

## 阶段 4：动态容量读取与保守纠错

### 4.1 动态目标

分别读取以下标题中斜杠后的分母：

- 主军兵种上限；
- 主法术上限；
- 自带攻城机器上限；
- 援军兵种上限；
- 援军法术上限；
- 援军攻城机器上限。

固定的 `352/11/3/55/4/2` 只能作为当前测试样本的期望值和 OCR 合理性先验，不得作为所有用户截图的硬编码目标。

若分母无法可靠读取：

- 不做容量驱动自动修正；
- 保留视觉类别和数量候选；
- 显示“容量上限不可读”；
- 交由人工审核。

### 4.2 纠错顺序

按照以下顺序处理：

1. 保留高置信类别；
2. 拒绝明显超出该类别可行范围的数量；
3. 使用 OCR Top-K、数字分割和重新预处理结果寻找数量替代；
4. 选择改动最少且唯一满足分母容量的数量组合；
5. 若数量无法唯一解决，只对低置信类别查看其视觉 Top-K；
6. 只有替代类别本身有足够视觉证据且产生唯一稳定解时才允许改类别；
7. 多解、弱证据或需要改动多个高置信类别时保持待确认。

### 4.3 明显错误规则

以下结果不得继续显示为普通可信候选：

- 单个卡片数量已超过该区域容量上限；
- 数量乘住房空间已经超过整个区域上限；
- 调试框序号与 `xN` 拼接形成的两位数；
- OCR 值与其他预处理候选差异极大且置信度不稳定；
- 当前组合出现 1787、555、61、35、375 等明显越界容量。

明显错误可被高质量备选自动替换；没有可靠备选时必须清空数量并要求人工填写。

### 4.4 自动修正记录

审核界面必须区分：

- 视觉原始值；
- 容量修正值；
- 修正原因；
- 是否唯一解；
- 用户是否已确认。

## 阶段 5：装备 ONNX 主导与英雄归属容错

### 5.1 来源策略

- ONNX 正常运行时，正式候选只来自 ONNX；
- 模板同时运行但仅记录影子 Top-K；
- 模板与 ONNX 分歧不能改变正式排序；
- ONNX 不可用时，模板候选标记为 `degraded-review-only`；
- 降级模板候选不得自动确认装备或英雄。

### 5.2 单槽高置信锚点

“高置信”必须同时满足：

- 裁片几何质量合格；
- Top-1 绝对分达到经真实验证集校准的门槛；
- Top-1 与 Top-2 分差达到门槛；
- 模型输出没有异常饱和或分布外迹象。

不得直接沿用模板的 `1 - distance` 百分比作为 ONNX 阈值，也不得凭单张截图手调阈值。

### 5.3 两槽推断规则

每列按以下规则处理：

1. 两槽均为高置信且属于同一英雄：确定英雄并保留两件装备。
2. 两槽均为高置信但属于不同英雄：标记冲突，不允许模板覆盖或全局规则强行改写。
3. 仅一槽高置信：以该槽所属英雄为锚点，在另一槽的同英雄候选中选择视觉分最高者。
4. 第二槽同英雄候选仍需满足最低分、分差和裁片质量门槛；不满足则第二槽未知，英雄可显示为“由单件高置信装备推断，待核对”。
5. 两槽均不够高：允许计算合法装备对，但只有组合分和组合分差都达标才形成候选，否则整列待确认。
6. 不允许两槽选择同一件装备。

### 5.4 四列全局规则

- 英雄唯一性用于发现冲突和在接近候选间选优；
- 唯一性不能推翻单槽高置信证据；
- 无合法且可靠分配时保留未知；
- 不得为了得到四位不同英雄而把低分候选提升为确定结果；
- 战宠唯一性继续保留，但不参与决定英雄类别。

### 5.5 英雄推断边界

- 不使用英雄头像；
- 不使用皮肤视觉分类；
- 英雄只能由装备归属推断；
- 单件装备确定的英雄必须显示证据不完整状态；
- 两件可靠装备共同归属相同时，才允许进入完整自动候选状态。

### 5.6 分歧文案

禁止继续显示含糊的“来源：模板 · 与模板分歧”。建议分别显示：

- `正式来源：ONNX`；
- `模板影子结果：一致/不一致`；
- `ONNX 不可用：当前仅显示模板审核候选`；
- `两槽英雄归属冲突，未自动选择`。

模板相似度不得与 ONNX 概率使用相同百分比语义。

## 阶段 6：审核体验和拒识门禁

审核页至少提供：

- 面板框和布局是否确定；
- 原始卡片类别/数量；
- 自动修正后的类别/数量；
- 动态容量分母及读取置信度；
- 装备 ONNX Top-K；
- 模板影子 Top-K；
- 单件装备是否被用作英雄锚点；
- 第二件装备是否受英雄归属过滤；
- 待确认、冲突、几何错误和模型不可用状态。

以下情况必须阻止“一键确认全部”：

- 面板或布局不确定且会改变识别结果；
- 容量分母不可读且存在数量异常；
- 明显越界数量仍未解决；
- 装备跨英雄冲突；
- 第二件装备证据不足；
- 重复英雄、重复装备或重复战宠；
- 模板降级结果尚未人工确认。

逐项人工修正必须始终可用。

## 阶段 7：测试重建

### 7.1 强回归 E2E

11 张干净截图逐张断言：

- 图像哈希与标签匹配；
- 正确布局；
- 面板边界指标；
- 每个区域卡片数量；
- 每个卡片类别和数量；
- 每个容量分母及最终容量；
- 四列英雄归属；
- 两件装备结果或明确待确认；
- 战宠和咏王模式（标签可确认时）；
- 是否允许一键确认。

不得只断言“存在几个框”或“页面没有报错”。

### 7.2 样本 7 压力测试

至少断言：

- 不把调试框序号与 `xN` 拼接成可信数量；
- 不产生超过动态容量上限的已确认结果；
- 无法分离时进入待确认；
- 黑边和字幕不会成为面板边界。

### 7.3 旧数据集

- 第一批和第二批样本继续作为兼容回归，但报告必须明确其是否参与模板/reference 构建；
- 第二批评估必须增加明确 `expect` 门槛，不能只写 JSON；
- 预裁模型一致性测试继续保留，但不得被描述为端到端准确率；
- 独立截图不得加入模板或训练集后仍继续作为盲测样本。

### 7.4 单元测试

至少覆盖：

- 每个面板候选分别评估布局；
- 绿色/浅色进攻按钮；
- 面板低分差拒识；
- 手动框锁定与布局重算；
- 调试序号和数量徽标分离；
- 动态分母读取；
- 数量优先纠错；
- 多解时不纠错；
- ONNX 与模板分歧不回退；
- 单槽高置信英雄锚点；
- 第二槽低分时保持未知；
- 两槽高置信跨英雄冲突；
- 四列唯一性不能强推低分结果。

## 8. 验收门禁

## 门禁 A：标签可信

- 11 张干净截图标签完整；
- 标签不是由当前机器结果复制；
- 卡片类别、数量和容量人工复核；
- 面板框叠加图可视检查通过。

## 门禁 B：布局与面板

- 11/11 布局正确；
- 11/11 面板 IoU 和边误差达标；
- 面板候选低分差时状态可见；
- 手动框不会被覆盖。

## 门禁 C：卡片与容量

- 11/11 卡片槽位、类别和数量与标签一致；
- 11/11 动态容量分母正确；
- 最终容量与分母一致；
- 不存在已确认的明显越界数量；
- 自动纠错都有原始证据和唯一解说明。

## 门禁 D：英雄与装备

- 11/11 四列英雄不发生错误自动归属；
- 高置信装备结果与标签一致；
- 证据不足时允许待确认，但不得自动归到错误英雄；
- ONNX/模板分歧不会触发模板覆盖；
- 单槽锚点和第二槽过滤行为可诊断；
- 不使用英雄头像或皮肤分类。

## 门禁 E：压力样本

- 样本 7 不产生可信的 `55/31/51/62` 等拼接数量；
- 无法可靠识别时进入人工审核；
- 污染标记不会成为面板或卡片结构锚点。

## 门禁 F：兼容性与构建

- 现有独立样本不低于稳定基线；
- 单元、组件和 E2E 全部通过；
- 浏览器和 Tauri 构建通过；
- 离线模型加载通过；
- Release Candidate 烟雾测试通过。

任一质量门禁未通过时，不得通过降低断言、扩大坐标容差或把错误结果改成新期望来宣告完成。

## 9. 禁止实现方式

实施 agent 不得：

- 针对 `1.png`～`12.png` 文件名写分支；
- 为单张图硬编码面板坐标；
- 用固定 `352/11/3/55/4/2` 覆盖动态分母；
- 为凑容量修改多个高置信类别；
- 将模板结果伪装成 ONNX；
- 在 ONNX 与模板分歧时自动信任模板；
- 用英雄唯一性强行填满四列；
- 把模板相似度显示为校准概率；
- 用预裁模型准确率替代完整截图准确率；
- 将强回归图片加入训练/模板后仍称其为独立验证；
- 删除未知、冲突或拒识状态来提高表面覆盖率。
