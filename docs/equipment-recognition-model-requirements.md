# 英雄装备独立识别模型：任务需求与边界条件

## 1. 文档目的

本文档供后续实现、数据集制作和模型训练 agent 使用。目标是为英雄装备建立独立的图像识别模型，替代或增强当前基于 dHash + HSV 模板距离的装备识别流程。

本文档只描述装备模型本身，不要求在本任务中修改英雄全局推理、面板定位或识别审查 UI；这些模块需要通过明确接口与模型对接。

## 2. 为什么需要独立模型

当前装备识别依赖固定装备框、64×64 视觉特征、dHash 和 HSV 直方图最近邻匹配。该方案对以下变化敏感：

- 装备槽横向或纵向偏移；
- UI 缩放、设备分辨率变化；
- 截图或视频压缩；
- 等级数字、编辑铅笔等覆盖层；
- 颜色和轮廓相似的装备；
- 当前模板样本数量少、类别覆盖不均衡。

独立模型应提升“装备槽图像 → 装备 ID”的鲁棒性，但不能被视为整个截图识别问题的唯一修复。

## 3. 明确的任务边界

### 3.1 模型负责的事情

模型负责：

1. 对一个已经定位的装备槽裁片进行装备类别分类；
2. 输出装备 ID、候选列表和可比较的置信度/分数；
3. 对轻微裁剪偏差、缩放、压缩和 UI 覆盖层保持鲁棒；
4. 提供足够的 Top-K 候选，供后续英雄归属推理使用。

### 3.2 模型不负责的事情

模型不负责：

- 定位整个军队面板；
- 找到八个装备槽的位置；
- 修复装备槽框完全偏离目标的问题；
- 直接决定四列英雄最终归属；
- 解决四列英雄重复；
- 识别英雄皮肤或战宠；
- 在图片中完全没有目标装备时强行给出一个装备类别。

面板定位和装备槽局部校准应由上游几何模块处理；四列英雄不重复、两件装备同属一个英雄等规则应由下游全局推理模块处理。

## 4. 推荐模型任务形式

第一版采用“单装备槽、全装备类别、闭集分类”模型：

```text
输入：单个完整装备槽裁片
输出：当前版本全部装备类别的概率或排序
```

不建议第一版按英雄拆分为多个模型。统一分类器更容易维护，也能直接比较跨英雄的相似装备。

每个装备类别使用稳定 ID，例如：

```text
equipment_52
equipment_53
equipment_60
```

模型类别列表必须从当前项目装备目录自动生成，不能手写一份可能过期的列表。

## 5. 类别与未知结果设计

### 5.1 已知装备

当前版本装备目录中的每个装备 ID 对应一个类别。每个类别应附带以下元数据：

- `equipmentId`：装备 ID；
- `displayName`：显示名称；
- `ownerHeroId`：装备所属英雄 ID；
- `heroName`：装备所属英雄名称。

`ownerHeroId` 只能作为标签和下游推理元数据，不建议在第一版中把英雄归属单独编码成模型类别。

### 5.2 空槽

如果游戏界面允许出现空装备槽，可增加 `empty_slot` 类，并为其提供真实空槽样本。

如果上游几何模块已经保证槽一定存在，则不必加入空槽类别。

### 5.3 未知/损坏裁片

不要把所有异常图像混成一个普通的 `unknown_equipment` 类。以下情况更适合由拒识逻辑处理：

- 裁片只包含面板背景；
- 裁片严重偏离装备槽；
- 图标被完全遮挡；
- 图像过度压缩或损坏；
- 新版本尚未收录的装备。

模型应输出 Top-K 和分数，由上层根据绝对分数、Top-1/Top-2 分差和图像质量决定是否返回“待确认”。

## 6. 输入裁片标准

训练和推理必须使用完全一致的预处理流程。

推荐第一版标准：

- 输入包含完整装备卡片边框；
- 输入包含卡片内部背景和实际图标；
- 保留等级数字、编辑铅笔、边角标记等真实 UI 元素；
- RGB 三通道；
- 固定尺寸，例如 `96×96`；
- 保持原始宽高比后进行统一缩放；
- 不要把透明图标直接放在纯色背景上作为主要训练数据。

如果最终运行时继续采用项目已有的 `64×64` 归一化，则数据生成、训练和推理都必须统一为同一套 `64×64` 流程。尺寸本身不是关键，训练/推理一致性才是关键。

建议保留原始裁片信息，便于定位问题：

```json
{
  "image": "...",
  "equipmentId": 52,
  "ownerHeroId": 7,
  "sourceType": "real",
  "sourceScreenshot": "...",
  "layout": "saved",
  "device": "iphone-17",
  "cropRect": [0.1, 0.2, 0.04, 0.07],
  "cropOffsetPx": [0, 0],
  "scale": 1.0,
  "splitGroup": "screenshot-001"
}
```

## 7. 数据来源标准

### 7.1 合成数据

项目现有装备图标可以用于生成合成卡片，但必须先渲染成接近真实游戏的装备槽：

- 紫色装备卡片背景；
- 真实卡片边框；
- 等级数字区域；
- 编辑状态铅笔图标；
- 不同卡片缩放；
- 少量相邻卡片或面板背景；
- 与实际截图相近的抗锯齿和重采样效果。

不能主要使用“图标 + 白色/纯色背景”的数据，否则模型容易学习背景颜色和图标边界，遇到真实截图会失效。

### 7.2 真实数据

真实数据必须来自完整游戏截图中的实际装备槽，并经过人工确认标签。

建议最低标准：

- 每个装备类别至少 20 个不同真实裁片；
- 目标是每类 50 个以上真实裁片；
- 覆盖不同分辨率、设备、布局和截图压缩质量；
- 同一张截图的八个装备槽应保留原始截图分组信息；
- 误框、合框、严重截断的样本不得作为“正确装备”标签。

合成数据可以先用于模型启动，但正式验收必须以独立真实截图为准。

## 8. 数据增强规则

增强的目标是模拟真实误差，不是制造不可能的图像。

### 8.1 几何增强

建议覆盖：

- 横向偏移：`±8～12 px`；
- 纵向偏移：`±6～10 px`；
- 缩放：`0.94～1.06`；
- 宽高比变化：不超过 `±3%`；
- 轻微左右/上下边缘裁切；
- 不同目标分辨率下的重新采样。

这些范围应覆盖项目当前装备槽局部校准候选的偏移范围，并通过真实截图验证后再调整。

### 8.2 图像增强

建议覆盖：

- 亮度变化：约 `±15%`；
- 对比度变化：约 `±15%`；
- 饱和度变化：约 `±15%`；
- 轻微高斯模糊；
- JPEG 压缩质量变化；
- 轻微噪声；
- 截图二次缩放。

### 8.3 UI 覆盖层增强

应覆盖不同：

- 装备等级数字；
- 编辑铅笔标记；
- 卡片边框亮度；
- 装备槽周围背景；
- 相邻卡片边缘进入裁片。

不建议使用大角度旋转、强烈透视、严重色相改变或完全遮挡图标的增强。

## 9. 类别平衡与难例集

### 9.1 类别平衡

每个装备类别的训练样本数量应尽量接近。不能因为某些装备已有官方图标，就让它们的样本数量远高于其他类别。

合成数据应按类别均衡生成；真实数据不足的类别可以先用合成数据补齐，但必须在报告中标记真实样本比例。

### 9.2 难例集

必须单独收集并标记以下难例：

- 同一英雄下外观相近的装备；
- 不同英雄但颜色相近的装备；
- 当前模板匹配 Top-1 与 Top-2 分差小于 5% 的样本；
- Dragon Duke、Grand Warden、Barbarian King 等容易互相混淆的装备；
- 不同等级数字和编辑标记下的同一装备；
- 轻微错位后仍然可人工识别的裁片。

难例不能全部放入训练集，必须保留一部分作为独立测试集。

## 10. 数据切分规则

不能把同一张原图裁成多个偏移版本后随机分到训练集和测试集，这会造成数据泄漏。

规则如下：

```text
同一原始截图生成的所有裁片和增强版本必须属于同一个 splitGroup
```

建议比例：

- 训练集：70%；
- 验证集：15%；
- 测试集：15%。

测试集应包含训练中未出现过的：

- 原始截图；
- 设备；
- 分辨率或缩放比例；
- 页面布局；
- 压缩质量；
- 裁剪偏移组合。

## 11. 推荐输出接口

模型适配层至少应返回：

```ts
interface EquipmentPrediction {
  id: number
  score: number
  ownerHeroId: number
}

interface EquipmentRecognition {
  candidates: EquipmentPrediction[]
  top1?: EquipmentPrediction
  source: 'onnx' | 'template'
  modelVersion: string
  preprocessingVersion: string
}
```

要求：

- `candidates` 按分数降序排列；
- 至少返回 Top-3，建议返回 Top-5 或 Top-8；
- 分数必须能在同一次模型输出中比较；
- 不要把分数直接解释为真实概率，除非做过校准；
- 模型不可用时保留模板识别兜底；
- 模型输出应保留原始分数，便于离线分析。

## 12. 与英雄推理模块的边界

模型输出装备候选后，下游不应简单地“每个槽取 Top-1，再判断两件装备归属”。推荐由下游完成：

1. 对每列枚举各英雄可形成的两件不同装备组合；
2. 计算该列属于每个英雄的组合分数；
3. 对四列联合求解，保证英雄不重复；
4. 证据不足时保留未知，而不是强行选择低分英雄；
5. 确定英雄后，再从该英雄的候选装备中选择具体装备。

装备模型只提供证据，不负责强制满足四列唯一性。

## 13. 置信度与拒识标准

第一版必须支持拒识，不能无条件输出一个装备。

至少应同时考虑：

- Top-1 绝对分数；
- Top-1 与 Top-2 的分差；
- 图像有效区域比例；
- 裁片是否存在严重边缘截断；
- 同一列两件装备能否形成合法同英雄组合。

示例逻辑：

```text
Top-1 72%，Top-2 51% → 可作为自动候选
Top-1 61%，Top-2 59% → 待确认
Top-1 48%，Top-2 44% → 待确认
```

实际阈值必须根据独立真实验证集统计，不能仅凭合成数据设定。

## 14. 评估指标与初始验收目标

不要只报告整体 Top-1。至少报告：

1. 装备 ID Top-1；
2. 装备 ID Top-3；
3. 装备所属英雄 Top-1；
4. 轻微框偏移后的准确率；
5. 每个装备类别的召回率；
6. Top-1/Top-2 分差分布；
7. 拒识准确率和误拒率；
8. 四列经过英雄唯一匹配后的整组准确率。

第一版可参考以下验收门槛：

- 干净真实裁片 Top-1：不低于 95%；
- 轻微框偏移真实裁片 Top-1：不低于 90%；
- Top-3：不低于 98%；
- 英雄归属准确率：不低于 97%；
- 任一装备类别召回率：不低于 90%。

最终是否达标必须以独立真实测试集为准。若整体指标较高但某一类召回率很低，不能视为模型合格。

## 15. 必须覆盖的边界情况

训练和测试计划必须明确覆盖以下情况：

- 裁片横向偏移但图标仍完整；
- 裁片纵向偏移但图标仍完整；
- 裁片轻微截断卡片边缘；
- 装备等级数字变化；
- 编辑模式与已保存模式；
- 进攻确认页面与普通军队页面；
- 不同设备和分辨率；
- 黑边、字幕或视频画面边缘存在；
- JPEG 二次压缩；
- 相邻装备卡片边缘进入当前裁片；
- 装备图标严重模糊；
- 图标缺失、空槽或面板背景误框；
- 新装备未加入类别列表；
- 模型 Top-1 与 Top-2 分数接近；
- 四列中多个槽都偏向同一英雄；
- 正确装备只出现在 Top-4～Top-8；
- 同一装备被错误识别为另一英雄的装备。

## 16. 交付物

实现 agent 至少应交付：


- 数据集生成或整理脚本；
- 数据集 manifest；
- 类别映射文件；
- 训练/验证/测试划分报告；
- 模型文件及版本信息；
- 预处理版本说明；
- 独立真实测试结果；
- 混淆矩阵或主要混淆对；
- 推理适配层；
- 模型不可用时的模板兜底方案；
- 对上述边界情况的覆盖说明。

## 17. 推荐实现阶段

### 阶段一：数据管线

先实现类别自动读取、合成卡片渲染、真实裁片导入、增强和按原图分组切分。此阶段不应修改线上识别流程。

### 阶段二：基线模型

使用统一输入预处理训练第一版模型，与现有模板法在同一独立真实测试集上对比。

### 阶段三：模型适配

增加 ONNX 推理适配层，保留现有模板识别作为降级路径，并输出 Top-K 诊断信息。

### 阶段四：下游联合推理

再将装备候选交给四列英雄唯一匹配逻辑。不要在模型训练任务中直接修改英雄归属规则。

## 18. 最重要的验收原则

1. 合成数据高分不等于真实截图可用；
2. 同一张原图的增强版本不能跨 split；
3. 模型必须允许返回“待确认”；
4. 装备分类、装备归属和英雄唯一性是三个不同层次的问题；
5. 正确的 Top-K 候选但错误的 Top-1，说明模型还有利用价值，但下游必须采用全局推理；
6. 如果裁片框已经完全错误，不能要求装备模型承担定位职责；
7. 所有阈值都应由独立真实验证集确定。
